# Z030: `deinit` should leave the receiver in a terminal state

Detects `deinit` functions with pointer receivers that never put the receiver
into a terminal state. The diagnostic uses the receiver's actual parameter
name and reads `deinit should leave <receiver> invalid, empty, or destroyed`,
followed by a reason when the linter has one. Leaving a caller-owned receiver
in a terminal state is a Zig convention that helps catch use-after-free bugs
during development.

## Terminal states

A receiver is in a terminal state when the function does any of the following:

- poisons the whole receiver with `self.* = undefined`
- destroys the receiver, ending its lifetime
- resets a lifecycle field to its empty or closed value (`self.active = false`,
  `self.closed = true`, `self.owner = null`, `self.state = .closed`, ...)
- resets a slice-typed receiver field to an empty slice
- calls a receiver method that this analysis can itself prove leaves the
  receiver terminal, which is how idempotent cleanup such as
  `if (!self.active) return; self.active = false;` is accepted
- wins an atomic compare-exchange close when the receiver's closed-state
  predicate matches the value being exchanged

The terminal state must be reached on every path that can fall through. A
`return` taken before the receiver is terminal is still reported, and so is a
write to a receiver field that would run after the receiver has been destroyed.

## Examples

### Bad

Missing `self.* = undefined`:

```zig
// expect: Z030
const Foo = struct {
    data: []u8,
    allocator: std.mem.Allocator,

    fn deinit(self: *Foo) void {
        self.allocator.free(self.data);
    }
};
```

Early return without defer:

```zig
// expect: Z030
const Foo = struct {
    data: ?[]u8,
    allocator: std.mem.Allocator,

    fn deinit(self: *Foo) void {
        if (self.data == null) return;
        self.allocator.free(self.data.?);
        self.* = undefined;
    }
};
```

### Good

Set `self.* = undefined` at the end:

```zig
const Foo = struct {
    data: []u8,
    allocator: std.mem.Allocator,

    fn deinit(self: *Foo) void {
        self.allocator.free(self.data);
        self.* = undefined;
    }
};
```

Use `defer` to handle all code paths:

```zig
const Foo = struct {
    data: ?[]u8,
    allocator: std.mem.Allocator,

    fn deinit(self: *Foo) void {
        defer self.* = undefined;
        if (self.data) |d| {
            self.allocator.free(d);
        }
    }
};
```

Heap-allocated receivers may end their lifetime by destroying themselves. In
that case, no invalidating write is needed:

```zig
const Foo = struct {
    fn deinit(self: *Foo, allocator: std.mem.Allocator) void {
        allocator.destroy(self);
    }
};
```

If both operations are used, invalidation must happen before destruction and
the allocator must not be read from the invalidated receiver:

```zig
const Foo = struct {
    allocator: std.mem.Allocator,

    fn deinit(self: *Foo) void {
        const allocator = self.allocator;
        self.* = undefined;
        allocator.destroy(self);
    }
};
```

Non-pointer receivers are not checked:

```zig
const Foo = struct {
    data: u32,

    fn deinit(self: Foo) void {
        _ = self;
    }
};
```

## Rationale

Setting `self.* = undefined` after deinitialization is a Zig idiom that helps catch use-after-free bugs:

1. **Debug safety**: In debug builds, accessing `undefined` memory triggers a panic, making bugs immediately visible
2. **Valgrind/ASan friendly**: Undefined memory is more likely to be detected by memory sanitizers
3. **Convention**: This pattern is used throughout the Zig standard library

When a `deinit` function has early returns, using
`defer self.* = undefined;` ensures all code paths properly invalidate the
struct. Do not use this pattern when the function destroys `self`: the
deferred write would run after the receiver's allocation has been freed.

An early-return branch that explicitly invalidates the receiver before returning is also accepted.
